# Киноманьяк

Подбор фильма по сложному запросу только из своего каталога `films.json` (52 фильма, 12 казахстанских).
Модель возвращает только id фильмов, код проверяет каждый id по каталогу и печатает название, год, минуты
и описание из каталога. Сгенерировать фильм, которого нет в каталоге, программа не даст.

## Достигнутые уровни

- **Common: выполнен.** Каталог, запуск, промпт, проверка id кодом, журнал, `show.py`, `queries.json`,
  `check.py`, тесты, опыт с памятью модели.
- Rare, Epic, Legendary: не выполнены.
- Автопроверка `kino_check.py`: Common (S01–S21) и живой прогон (`--live`, V00–V05) пройдены.

## Пять вопросов лекции 1 для этой задачи

Вопросы со слайда «Продуктовый челлендж» лекции 1, если забыть про слово AI/ML.

1. **Какую цель преследуем?** Из каталога на 52 фильма выбрать от одного до трёх под запрос на естественном
   языке, например «фантастика не про космос» или запрос на казахском. Если подходящего фильма нет, честно
   сказать об этом.
2. **Как задача решается без AI/ML?** Фильтры по полям каталога (год, минуты, жанр, страна, язык) и поиск слов
   в описании: правило или простой поиск до вызова модели. Оно закрывает запросы вида «на корейском»,
   «до полутора часов», «фантастика семидесятых».
3. **Какие данные и знаем ли мы их заранее?** Каталог известен заранее: `films.json` с id, названием, годом,
   минутами, жанрами, странами, языками, описанием и источником. Год, минуты, страны и языки взяты из Wikidata,
   не из памяти модели (см. «Источник каталога»). Запрос становится известен только в момент вызова, поэтому
   заранее его не разобрать.
4. **Что должна выдать модель?** Не фильм целиком, а от одного до трёх id и по короткой причине `why`, либо
   статус `no_match`. Название, год, минуты и описание печатает код из каталога. Если ответ модели не прошёл
   проверку, пользователь видит сообщение об ошибке.
5. **Стоимость ошибки.** Ошибки разной цены. Выдуманный или перепутанный фильм ломает доверие к подбору,
   поэтому такой ответ пользователь не видит вообще. Неподходящий фильм среди настоящих (не тот жанр) дешевле:
   фильм существует, его данные верны, и запрос можно уточнить.

## Запуск

```bash
uv sync
cp .env.example .env     # вписать OPENAI_API_KEY; без ключа работает локальная модель
```

Локальная модель `qwen3.5:4b` через Ollama. Каталог в промпте занимает около 6 000 токенов, окно по
умолчанию 4096 слишком мало, сервер запускается так:

```bash
OLLAMA_CONTEXT_LENGTH=16384 ollama serve
```

```bash
uv run kino.py "фильм как Интерстеллар, но не про космос"   # облако, при сбое облака локальная
uv run kino.py --local "запрос"                              # только qwen3.5:4b
uv run check.py                                              # прогон queries.json, облако
uv run check.py --local                                      # то же на qwen3.5:4b
uv run show.py                                               # итоги по журналу calls.jsonl
uv run memory_test.py [--local]                              # опыт с памятью модели
uv run pytest -q                                             # 109 тестов, без сети
uv run build_catalog.py                                      # пересборка films.json из Wikidata
```

### Ограничение схемы: не больше трёх фильмов

Единственный `invalid` в журнале: `qwen3.5:4b` вернула больше трёх фильмов на запрос «Комедия про Россию или СССР,
не американская», код ничего не показал. При запуске `kino_check.py --live` та же модель на запросе
«Что-нибудь до полутора часов, только не комедия» дважды не уложилась в 180 с, отведённые проверкой на один
запрос. Я воспроизвёл вызов отдельно: из четырёх запусков в трёх модель перечисляла 18–23 фильма
(600–770 токенов, 114–173 с).

Поэтому в схему ответа добавлено `max_length=3` ([kino.py:46](kino.py#L46)): модель получает `maxItems: 3` и
не может вернуть больше трёх. После этого тот же запрос на четырёх запусках шёл 15–20 с и всегда возвращал три
фильма. Облачная модель такую схему принимает. Проверка `check_ids` на «больше трёх» осталась как вторая линия.
Третий прогон `queries.json` сделан уже на этой схеме: среднее время запроса на `qwen3.5:4b` 51 с (CPU,
Intel i5), максимум 69 с; до ограничения отдельные ответы шли до 182 с. На `gpt-6-luna` в среднем 2,0 с.

Чужих id реальные модели не вернули ни разу, эта защита проверяется тестами с заглушкой.

### Опыт с памятью модели

`memory_test.py` просит модель без каталога назвать год и минуты 10 фильмов из каталога
(каждый пятый, [memory_test.py:29](memory_test.py#L29)) и сверяет ответы с `films.json`
([memory_test.py:69](memory_test.py#L69)).

| Модель | Год не совпал | Минуты не совпали |
|---|---|---|
| `qwen3.5:4b` | 3 из 10 | 8 из 10 |
| `gpt-6-luna` | 0 из 10 | 3 из 10 |

Например, `qwen3.5:4b` назвала «Подарок Сталину» фильмом 1956 года (в каталоге 2008) и «Брата» на 146 минут
(в каталоге 95).

## Источник каталога

- Год, минуты, страны, языки и жанры: [Wikidata](https://www.wikidata.org) (данные под CC0), запрос SPARQL
  в [build_catalog.py:52](build_catalog.py#L52). В поле `source` каждого фильма стоит его страница Wikidata.
- Список из 52 фильмов задан вручную в `build_catalog.py` (название и год). Жанры, страны и языки приведены
  к словам каталога таблицей соответствий в том же файле.
- «Бизнес по-казахски» (2016): в Wikidata нет длительности, поэтому взят из примера курса
  `data/films_kz_example.json` (источник в `source`: статья в английской Википедии).
- Описания (`descriptions.json`) написаны по вступлению статей русской Википедии, одно-два предложения.
  Остальные поля в них не попадают.
- В примере курса для двух фильмов данные отличаются от Wikidata: «Томирис» 156 минут против 155,
  «Жаужурек мын бала» 2012 год против 2011. В каталоге значения из Wikidata.
- Исходные ответы Wikidata лежат в `data/wikidata.json`, каталог пересобирается командой `uv run build_catalog.py`.

## Ответы на вопросы

**1. Почему программа сверяет id, хотя название понятнее? Сколько расхождений с каталогом дал опыт с памятью?**
Название модель может исказить или выдумать, а id проверяется точным сравнением со множеством id каталога
([kino.py:83](kino.py#L83)). Названия, годы и описания для печати берутся из каталога по проверенному id
([kino.py:155](kino.py#L155)), модели вручную ничего не доверяется. Опыт с памятью показал:
`qwen3.5:4b` ошиблась в годе у 3 фильмов из 10 и в минутах у 8 из 10, `gpt-6-luna` в годе у 0 и в минутах у 3.
Даже сильная модель путает минуты, поэтому данные фильма не берутся из ответа модели.

**2. Что произойдёт, если модель вернёт `film_id`, которого нет в каталоге? Какие строки кода это ловят?**
`check_ids` собирает множество известных id и отбирает чужие ([kino.py:85](kino.py#L85),
[kino.py:87](kino.py#L87)). `pick` получает причину и список чужих id и возвращает исход `invalid` с пустым
списком ([kino.py:151](kino.py#L151)). Печать фильмов стоит после этой проверки ([kino.py:155](kino.py#L155)),
поэтому пользователь не видит ни одного фильма, даже настоящего. Чужие id пишутся в журнал в поле `rejected`
([kino.py:69](kino.py#L69)). Поведение закреплено тестом [tests/test_pick.py:65](tests/test_pick.py#L65).
Тот же `invalid` получают повтор id и пустой выбор ([kino.py:90](kino.py#L90)-[kino.py:93](kino.py#L93)).
Больше трёх фильмов не пропускает уже схема ответа ([kino.py:46](kino.py#L46)), `check_ids` проверяет это повторно.

**3. Чем «модель ответила без ошибки» отличается от «модель подобрала верный фильм»? Как это видно в `check.py`?**
Исход `ok` означает только, что ответ по схеме и все id из каталога. Подходит ли фильм под условия, код по
исходу не знает. `check.py` считает их отдельно: сначала исходы ([check.py:44](check.py#L44)), затем подбор
через `judge` ([check.py:11](check.py#L11)): нужен совпавший исход, хотя бы один id из `must` и ни одного из
`forbid`. В третьем прогоне `qwen3.5:4b` дала 11 исходов `ok` и 4 `no_match`, но верно подобрала фильмы только в 13
запросах из 15: в двух ответах `ok` выбраны не те фильмы. Например, на «Короткий фильм до полутора часов» она
ответила `ok` и предложила «12 разгневанных мужчин» (95 мин), «Психо» (109 мин) и «Сияние» (119 мин): ответ без
ошибки, но все три фильма длиннее полутора часов.

**4. Какое решение без ML записано в пяти вопросах лекции 1 и чего ему не хватает на запросах из `queries.json`?**
Фильтры по полям каталога и поиск слов в описании (вопрос 2 выше). Они справляются с запросами, где условие
лежит в одном поле: «на корейском языке», «короткий фильм до полутора часов», «фантастика семидесятых годов»,
«на казахском». Не хватает смысла: «не про космос» требует понять по описанию, о чём фильм; «кроме
мультфильмов» не выражается полями, потому что жанра «мультфильм» в каталоге нет; «Голливуд емес»
переводится в страну только пониманием слова; запросы на казахском требуют читать текст запроса. Это оценка по
составу `queries.json`, отдельно она не измерялась.

**5. Сколько стоит один запрос и что сильнее всего влияет на цену?**
Запрос на `gpt-6-luna` стоит $0.000637 (30 запросов, всего $0.019104, по таблице цен `PRICE`,
[kino.py:16](kino.py#L16)). На запрос уходит в среднем 6 022 токена на входе и 61 на выходе: вход занимает
около 95% цены. Весь вход это каталог, который целиком идёт в промпт ([kino.py:49](kino.py#L49)), поэтому
цена растёт вместе с каталогом. Локальная `qwen3.5:4b` стоит $0, но платой становится время: 64 с на запрос.
